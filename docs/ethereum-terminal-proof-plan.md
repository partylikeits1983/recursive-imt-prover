# Ethereum verification plan for the 64 leaf root

Release requires Solidity to verify the recursive IMT prover’s final root proof directly against the application’s expected 64-leaf batch and a pinned merge authority. The hard limit is **under 11,000,000 gas** in one ordinary Ethereum transaction, including calldata. The engineering target is **under 10,000,000 gas**. The prover emits a verifier-independent proof. The release path uses no elliptic curves. Pool state updates and payments have a separate cost.

## Native verification on Ethereum

The 64 root-only clients averaged 4.10 seconds each and their 62 interior aggregates averaged 9.42 seconds. On the same two subtrees the midpoint profile produced a 316,380-byte root in 45.33 seconds. The complete Solidity verifier accepted it in a high-limit Prague transaction at **106,637,610 gas** with a fixed Merkle cap and public ring-weight certificate. Its 314,724 bytes of calldata cost a minimum of **12,464,520 gas**. Certifying the native row folds separately reduced the complete call to **104,570,178 gas** and raised its calldata to **443,108 bytes**. The single-verifier witness places all 169 folded rows and checkpoints for 9,905 Keccak permutations under one commitment. The next constraint must link the queried words and Merkle paths to the corresponding hash inputs and outputs so the EVM can omit those bytes. [Full receipts and reproduction](ethereum-root-verification.md#end-to-end-solidity-measurement)

The shared prime-field experiment verifies all 169 native row folds and every Keccak-f transition in the single-verifier trace with one WHIR opening. Its component receipt is **13,437,067 gas**. To remove raw rows from the full call, assign each of the 169 rows a fixed layout of three Keccak permutations. For the first 71 queries these are the two rate blocks of the 256-byte main leaf and the single block of the 128-byte fixed leaf. Each of the other 98 queries uses three blocks for a 384-byte leaf. This covers exactly **507 permutations** and **240 digests**. Constrain Ethereum Keccak padding, the rate XOR and capacity continuation between blocks, the link to the same 48 words used in the native row fold, and the 32 digest bytes selected by the native Merkle authenticator. Only after this relation verifies can the call replace the 64,896 raw bytes with 7,680 digest bytes. The remaining native Merkle paths, transcript and recursive arithmetic still need a compact proof. [Joint proof and measurements](ethereum-root-verification.md#certifying-the-native-whir-row-folds)

The 43,342 Keccak calls in the actual merge fit in one 22-variable large-prime checkpoint table when each scalar carries two 64-bit lanes. One opening of this table took 13.11 seconds to prove and 7,017,857 gas to verify on Osaka. The node-port entry point checks the final hash input and digest for both child roles in 7,133,812 gas on Osaka. The remaining relation must enforce the Keccak transitions and bind every active table to both cyclic child verifications. Allowing either the commitment or its claimed evaluation to be chosen independently of that relation would omit the child checks. [Checkpoint receipts and reproduction](ethereum-root-verification.md#large-prime-opening-on-the-actual-terminal-checkpoint-table)

Nine checkpoints per permutation fit in a 22-variable table using seven 240-bit chunks per state. Solidity checks the public checkpoint rows, authenticates the two endpoint readings, and reduces all 524,288 three-round segments to claims about their input bits. The linked call cost **9,080,519 gas** at rate 1/32 and **9,755,891 gas** at rate 1/16. The smaller call carried 204,260 bytes. The local WHIR target was 135 bits in both cases. Closing the returned input-bit claims and enforcing the two recursive child verifications remain necessary for settlement. [Checkpoint and transition measurements](ethereum-root-verification.md#three-round-keccak-segments)

On ordinary Osaka, `TerminalNibbleVerifier.verifyTransitions` verified all 24 Keccak rounds, both endpoints, node and padding inputs, and digit range on the actual 65,536-row table for **9,980,866 gas** (221,604 calldata bytes). This leaves 1,019,134 gas for both child verifications and their hash-port wiring. The lowest complete strong-profile receipt uses **104,570,178 gas** on high-limit local Prague. The checkpoint commitment and its opening each took about 15½ minutes on five M2 Pro threads. [Full witness, timings and reproduction](ethereum-root-verification.md#four-bit-digits-at-full-root-size)

In an isolated Rust run, increasing the four-variable profile’s maximum grinding to 20 kept the 152-bit local target and reduced the native proof to 346,304 bytes. Its 13,831,850 gas calldata floor excludes ABI framing. Lowering the local target to LeanVM’s 125 bits gave a 121.48-bit conditional native terminal bound. Proven knowledge soundness of the full recursive tree and statistical ZK for the client remain release requirements. [Matched security comparison](ethereum-root-verification.md#effect-of-changing-the-security-target)

The dedicated terminal circuit verifies two 32-leaf cyclic child proofs under a fixed child key and count. On a fresh 64-leaf tree built with packed masked record proofs, the separate-opening profile produces **633,632 bytes** with a **25,287,260 gas calldata floor**. The experimental shared opening produces **351,840 bytes** with a **14,052,630 gas floor** in 202–232 seconds on the same children. On those same two children the cyclic final proof takes 15.2–30.0 s and the dedicated terminal proof takes 37.7 s. The latter saves 33.2% in bytes. Solidity reproduced all 24 linked Keccak layers and authenticated the queried Merkle rows in component tests. Even after specializing two fixed linear maps, a full 24-layer call on the original verified terminal fixture uses **55.27M execution gas** in simulation. A native terminal design that meets 11M must reduce the field work and authenticated bytes together. [Dedicated terminal results](ethereum-root-verification.md#dedicated-terminal-merge)

Solidity implements the ordered batch digest and authenticates the native additive WHIR Merkle openings. A local replay checked all 956 queried rows from a real 64-leaf root across ten commitments. The 12,604 sibling hashes alone incur a one-transaction calldata floor of **16,106,570 gas**. The full saved proof incurs **37,855,080 gas** before verification. The opening format must change to meet the release limit. Splitting bytecode across contracts addresses deployment limits independently. The shared-opening and midpoint profiles have complete Solidity verification measurements above. [Measurements and replay](ethereum-root-verification.md#solidity-replay-of-native-openings) · [Solidity verifier crate](../crates/evm-verifier/)

At the native merge’s padded Keccak size, the IMT experiment verifies two 12-round segments together and cuts 1,381 non-PCS scalars. The serialized Keccak component shrinks by 5%. The larger target is the commitment layout and authenticated fixed wiring. [Current LeanVM source comparison and measured IMT controls](ethereum-root-verification.md#what-transfers-from-leanvm-to-a-fixed-imt-circuit)

The single-opening experiment reduced 134 bit readings to one on the real 64-leaf inputs. The resulting PCS component is 207,587 compressed bytes. The rest of the original aggregate still accounts for 143,850 separately compressed bytes. The measured floors together are about 14.04M gas with one transaction base, before a complete verifier can execute. Integrating this change alone would still miss the target on this decomposition. The next terminal benchmark should reduce the cost of the fixed wiring and linked Keccak checks together, using the IMT-specific layout. [Opening measurements](ethereum-root-verification.md#sharing-the-witness-and-wiring-opening)

The same depth-32 record replacement now runs on the pinned binary LeanVM. The M2 Pro comparisons include our masked client, our non-hiding fixed circuits, and the VM at matching code rates. Packed native inputs reduce the masked verifier product count from 3,457 to 2,181. The masked oracle still commits the full bit trace. A dedicated batched Keccak component needs to bind private checkpoint values to the path and masking transcript before it can serve as a client proof. [Leaf comparison and native tests](ethereum-root-verification.md#same-depth-32-leaf-in-the-current-binary-leanvm)

## LeanVM reference measurement

As a feasibility test, I split the complete upstream LeanVM grouped terminal verifier into six linked contracts. All six deployed through ordinary creation transactions on Anvil 1.5.1 with Osaka rules, standard size limits and `solc 0.8.28` (via IR, 833 optimizer runs, Cancun bytecode). One call verified the original 99,044 bytes of calldata. The benchmark uses LeanVM's own application root, a 100-bit terminal parameter and 28 grinding bits. Its manifest leaves full composition security unestablished. The entry contract links the constraint evaluator and WHIR opening verifier. They call libraries for arithmetic constraints, Merkle paths and polynomial weights. ## What the proof must authenticate

Start with the existing root statement. Each of the 64 leaves exposes a 32-byte membership root, input tag and output commitment. The tree binds their exact order using domain-separated Keccak leaf and node hashes and includes both child counts at each merge. The EVM entry point must obtain the expected batch digest from the application and compare it with the proof's public output. Accepting whichever digest a caller supplies would prove membership in a batch of the caller's choice. Fix the count to 64 and pin the inner verifier authority, outer program or circuit, and verifier module addresses. [Ordered statement](../src/binary/aggregation_tree.rs) · [Verifier authority](../src/binary/aggregation_tree/cyclic.rs)

For settlement, the pool must also enforce accepted anchors, spent tags and output insertion. Public deposits or withdrawals need asset, amount and transfer details bound to the actual Ethereum action. A private send can expose its spent tag and new commitment while keeping the amount and recipient inside the note. Bind the chain, pool and version where the spend is authorized if it must be usable only in that domain. Hashing a destination into an outer envelope alone lets someone rewrap the same domain-independent inner proof. Measure the pool's data publication, state writes and transfers alongside the verifier when evaluating the user's total fee. [Current child relation](protocol.md#child-statement) · [Current aggregation scope](binary-security.md)

`ImtBatchStatement.digest64(records)` implements the native ordered hash in Solidity for exactly 6,144 bytes of records. For the saved 64-leaf batch, a local Osaka transaction through a test harness returned the same digest as the Rust verifier and consumed **266,840 gas** for 6,212 calldata bytes. This measures statement hashing only. [Solidity implementation](../crates/evm-verifier/contracts/ImtBatchStatement.sol) · [Cross-runtime test](../crates/evm-verifier/test/ImtBatchStatement.t.sol)

## Gas budget

For an ordinary call, let `t = zero_calldata_bytes + 4 × nonzero_calldata_bytes`. Gas is `21,000 + max(10 × t, 4 × t + execution_gas)`. An internal call between libraries does not pay the transaction calldata floor again. At the strict 11M limit there is room for at most **274,474 all-nonzero bytes** including ABI framing. At the strict 10M target that falls to **249,474 bytes**. At 200,000 all-nonzero bytes the floor is 8,021,000 gas and execution must cost less than 7,779,000 gas to meet the 11M limit. [EIP-7623](https://eips.ethereum.org/EIPS/eip-7623)

## Release milestones

1. **Reduce the polynomial opening cost.** Measure main and preprocessing commitments independently at the existing security target. Test a final merge with its own parameters or representation. Account for every authenticated opening, transcript challenge and byte of the encoded proof. Enforce both the opening soundness bound and a practical prover memory budget before selecting the final parameters. [Opening breakdown and code-rate measurements](ethereum-root-verification.md)
2. **Verify the final proof in Solidity.** Pin the authority and proof version. Recompute the Fiat–Shamir transcript and verify the arithmetic, linked Keccak and polynomial-opening equations. Bind the expected 32-byte ordered digest and leaf count. Test honest fresh proofs and independent mutations of statements, openings and keys. Deploy with normal code-size limits. Record a successful ordinary transaction below 11M gas. [Native verifier](../crates/flock-backend/src/checkpoint.rs) · [Contract sources](../crates/evm-verifier/)
3. **Assess the same verification in LeanVM.** Measure native field operations, Keccak, guest cycles, proof bytes and prover resources. The theorem and expected authority must match the Solidity path. The complete certified Solidity verifier for one native midpoint root used 9,905 Keccak-f permutations in the opcode trace. A guest checking that proof also has to reproduce its binary-field arithmetic and all public bindings. The current guest exercises four sumcheck updates with host-supplied challenges. The upstream VM targets 125-bit ROM soundness and needs reconciliation with the repository’s 128-bit classical target. [Pinned LeanVM](https://github.com/leanEthereum/leanVM/tree/5b43139d50272f996ca884669b1d51555af1f35d)
4. **Substantiate production security.** Publish reproducible parameters and proof formats, reconcile component bounds across recursive levels, and review the verifier and privacy claims. Bound untrusted proof decoding and rerun cross-version fixtures when the key or format changes. [Security accounting](binary-security.md)

### Reproduce the verifier baseline and guest check

For the saved merge key, factoring the Keccak equality weights and reusing authenticated upper Merkle nodes reduced the circuit from 9,213,457 to 9,197,287 operations and from 21,832 to 21,670 Keccak permutations. These counts describe the recursive circuit. EVM gas and LeanVM cycles require separate measurements. The circuit count depends on the trusted merge key. Regenerate it from the benchmark key or the key from a new 64-leaf tree. The profile counts the operations to verify **one** root.

```sh
cargo run --locked --release --example root-verifier-profile -- --key "$KEY" --trusted "$TRUSTED_JSON"
cargo test --manifest-path adapters/leanvm/Cargo.toml --locked --release -- --nocapture
```

The current guest proves four consecutive evaluation-basis WHIR sumcheck updates captured while Rust verified the saved 64-leaf proof. Each input is three Poly64 coefficients. The public output commits to the initial claim, both round messages, the supplied challenge and the computed result of each round. The native trace supplies the expected output independently. The computation took **263 guest cycles** at all four code rates supported by the pin. The full root guest still needs to derive the challenges from the native Fiat–Shamir transcript and check the rest of the native proof. ## Where lattices could help

LaBinius is the closest match to this repository because its authors connected lattice commitments to the Flock binary proof front end. The verifier checks short polynomial vectors and modular equations. Those checks can run in ordinary EVM code. Its native evaluation field is GF(2¹⁶²), and the published field switch connects GF(2¹²⁸) front ends. Our verifier uses Poly64 and Poly192. The first design task is to specify and cost the reduction from our actual claims, including the main and preprocessing openings. [LaBinius paper](https://eprint.iacr.org/2026/2103) · [Construction and benchmarks](https://www.osdnk.me/blog/labinius)

| Candidate | What the authors measured | Consequence for this root |
| --- | --- | --- |
| LaBinius with LaBRADOR compression | 96.4 KiB, 729 ms native verification for 131,072 BLAKE3 compressions at a 100-bit target. The direct version used 5,130.3 KiB. | At 96.4 KiB of all-nonzero calldata, the illustrative floor is **3.97M gas**. The benchmark includes an analytic size estimate for the LaBRADOR component. Generate a real cross-process proof encoding before quoting transaction gas. [Benchmark](https://www.osdnk.me/blog/labinius) · [Size computation](https://github.com/osdnk/labinius/blob/96b57f724fc15c8e40495015c01dc3e6d8dfe595/crates/pcs/src/scheme/commitment.rs#L405) |
| LaBRADOR alone | The original paper reports 58 KB for an R1CS with roughly one million constraints, with verifier work linear in the instance size. | Translate our circuit and count modular operations. A short proof can still be expensive to check. [LaBRADOR paper](https://eprint.iacr.org/2022/1341) |
| Greyhound and RoKoko | Greyhound reports 53 KB for a polynomial evaluation up to degree 2³⁰. RoKoko reports roughly 200 KB for its structured relations with polylogarithmic verifier complexity. | Greyhound still needs the computation proof around it. RoKoko trades more calldata for lower verifier work. Benchmark either only with its complete terminal relation. [Greyhound](https://eprint.iacr.org/2024/1293) · [RoKoko](https://eprint.iacr.org/2026/575) |

Before relying on the LaBRADOR numbers, reconcile the November 2026 **LEASH** preprint with the exact implementation and parameters. Its authors report completeness counterexamples and issues with recursive transformations and knowledge-extraction bounds, and propose repairs. Check which findings apply to the selected compressor, then regenerate its size and operation counts at the chosen security target. [LEASH](https://eprint.iacr.org/2026/2898)

For a lattice prototype, count and benchmark the ring transforms and products, coefficient decoding, norm checks, challenge generation and fixed commitment-key access on the EVM. The reference compressor uses SHAKE and AES-based routines. Ethereum's Keccak opcode has a different interface and padding from SHAKE. Preserve the specified transcript or analyze any change to the protocol. Measure the complete lattice proof against the hash-based verifier on the same 64-leaf statement, with the same security target and public data. That receipt determines whether lattices reduce gas. [Reference compressor](https://github.com/osdnk/labinius/blob/96b57f724fc15c8e40495015c01dc3e6d8dfe595/crates/pcs/labrador/labrador.c) · [Measured EVM transform and SHAKE costs for a lattice signature](https://www.fireblocks.com/blog/post-quantum-signatures-ethereum-cheaper-gas)
